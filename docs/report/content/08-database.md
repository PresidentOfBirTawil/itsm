# Database design {#database .chapter}

Twenty-one tables, generated by Hibernate from the entity classes, so the code and the schema cannot drift apart. The same schema runs on H2 on a desktop and on PostgreSQL on a server.

![The central tables, their keys and relationships. Every table and column is in the two complete diagrams in Appendix C.](../diagrams/overview-database.svg){width=100%}

## The tables

::: {.compact}
| Table                                                    | Holds                                                                                      | Keys and constraints                                                      |
|----------------------------------------------------------|--------------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| `users`                                                  | Every account; one table for the whole class hierarchy                                     | `role` discriminator; unique `email`; BCrypt `password_hash`              |
| `technician_skills`                                      | Which categories each technician can handle                                                | (`technician_id`, `category_id`)                                          |
| `categories`, `category_keywords`                        | The nine categories and the words that suggest each one                                    | Unique `name`                                                             |
| `it_services`, `service_keywords`, `service_dependencies` | The service catalogue, the words people use for each service, and which service needs which | Unique `name`; `criticality` 1–3; (`service_id`, `depends_on_id`)        |
| `sla_policies`                                           | Response and resolution minutes per priority                                               | Unique `priority`                                                          |
| `incidents`, `incident_affected_users`                   | The incidents, with classification, priority assessment, deadlines, SLA state, outcome; who else is affected | Unique `code` from the sequence `incident_seq`; foreign keys to reporter, assignee, service, category, duplicate |
| `audit_entries`                                          | The audit trail: action, actor, time, old and new status, note                             | Never updated or deleted                                                   |
| `notifications`, `email_outbox`                          | In-app notifications and the simulated e-mails                                              | `read_at` null while unread                                               |
| `knowledge_articles`                                     | Knowledge base articles, with votes and views, optionally written from an incident           | Foreign keys to category, service, author, source incident                |
| `attachments`, `attachment_contents`                     | Files on incidents; the bytes in their own table so lists stay fast                         | Kind, size; unique `content_id`                                           |
| `api_tokens`                                             | API keys: only a SHA-256 hash, the visible prefix, expiry, last use, revocation             | Unique `token_hash`                                                        |
| `webhooks`, `webhook_events`, `webhook_deliveries`       | Webhooks, the events each wants, and the outbox that doubles as the delivery log            | Index on (`state`, `next_attempt_at`)                                     |
| `settings`                                               | Values changed at run time: assignment strategy, demo SLA                                  | Primary key `name`                                                         |
:::

## Important relationships

- An incident has exactly one reporter, one service, at most one category and at most one assignee, and may point to an earlier incident as a possible duplicate.
- An incident owns its priority assessment (embedded `priority_*` columns), its audit entries and its attachments: composition.
- All users live in one table; the `role` column tells JPA whether a row is an `Employee`, a `Technician` or an `Administrator`.
- Services form a directed graph through `service_dependencies`; the application refuses loops.
- Deadlines are copied from the SLA policy when an incident is prioritised, so changing a policy later never silently moves the deadlines of open incidents.

## Schema of the central table

::: {.schema}
```sql
create table incidents (
  id                     bigint not null primary key,
  code                   varchar(12)   not null unique,
  title                  varchar(150)  not null,
  description            varchar(4000) not null,
  reporter_id            bigint not null,  -- users
  assignee_id            bigint,           -- users
  service_id             bigint not null,  -- it_services
  category_id            bigint,           -- categories
  possible_duplicate_of_id bigint,         -- incidents
  duplicate_similarity   float(53),
  impact                 varchar(10) not null,
  urgency                varchar(10) not null,
  status                 varchar(20) not null,
  priority               varchar(5),
  priority_score         integer,
  priority_impact_weight integer,
  priority_urgency_weight integer,
  priority_criticality   integer,
  created_at             timestamp(6) not null,
  updated_at             timestamp(6) not null,
  acknowledged_at        timestamp(6),
  resolved_at            timestamp(6),
  closed_at              timestamp(6),
  response_due           timestamp(6),
  resolution_due         timestamp(6),
  sla_status             varchar(10),
  sla_paused_at          timestamp(6),
  sla_paused_seconds     bigint,
  response_breached_at   timestamp(6),
  resolution_breached_at timestamp(6),
  escalated_at           timestamp(6),
  resolution             varchar(1000),
  rating                 integer,
  rating_comment         varchar(1000),
  rated_at               timestamp(6)
);
```
:::

## Sample data

On first start Quell fills in the reference data. An administrator adds realistic incidents with one button (System → Settings → Reset and add sample incidents); each one is played through the real services, so it obeys every rule.

::: {.keys .compact}
| Data              | Contents                                                                                                                                          |
|-------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|
| Users             | 1 administrator; 4 technicians with different skills (network and hardware; database, storage and cloud; security, authentication and network; software, application and cloud); 4 employees |
| Services          | 7, with criticality and dependencies: Payment Application (3), Authentication Service (3), Database Cluster (3), Corporate Network (2), Cloud Storage (2), Email & Collaboration (1), Workplace Devices (1) |
| Categories        | The brief's nine (Hardware, Software, Network, Database, Cloud, Security, Authentication, Application, Storage), each with keywords                 |
| SLA policies      | The brief's four: P1 5 min / 30 min, P2 15 min / 2 h, P3 1 h / 8 h, P4 4 h / 24 h                                                                |
| Knowledge base    | 15 articles for common problems                                                                                                                  |
| Incidents         | 83: 23 stories in every status (a payment outage caused by the network, an escalated phishing wave, an incident nobody could take) and 60 resolved incidents over two months, for the learning features and the reports |
:::
